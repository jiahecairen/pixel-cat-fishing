# 需求对照表

来源：用户最初提供的《Fishing／Claude Code 项目完整交接档案》里的游戏设计部分，加上之后对话中用户提出的新需求。原档案中关于本地模型、Harness、AUTO-001/AUTO-002 调度器和审批流水线的内容，用户已明确不采用（"不打算使用本地 AI，由你来生成"），不在此表内。

状态含义：**已实现** = 代码写完且自动测试覆盖；**已实现·待实机** = 写完但只能在 macOS 上人工确认的部分还没确认；**部分** = 做了一部分；**未做**。

## 与原档案的偏差

- **#14 先落盘再发布状态**：原档案要求状态变更在成功写盘之后才对外生效。现在的做法是先改内存再写盘。这样做的原因是悬浮窗每帧都要显示最新状态，写盘失败时宁可让玩家继续玩并反复重试，也不回滚画面。代价是极端情况下（写盘持续失败后崩溃）会丢失最后几次变更。如果你要严格语义，我可以改成"变更先进待提交区，落盘成功后再合并"。
- **番茄钟、升级、小镇**都是原档案 v0.1 范围之外的新增内容，按对话中的决定实现。
- **工单与审批流程**（Phase A/B、APPROVALS 账本、Runner）没有沿用，改为：每个阶段做完跑测试、截图、提交、向用户汇报并等实机反馈。
